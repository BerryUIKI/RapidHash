# Checksum Format Specification

## 1. Scope

RapidHash reads and writes a conservative, documented subset of common checksum
formats. Parsing prioritizes safety and clear diagnostics over accepting every
ambiguous historical variant.

## 2. Initial Formats

| Format | Read | Write | Typical extensions |
| --- | --- | --- | --- |
| SFV | Supported | Supported | `.sfv` |
| GNU-style hexadecimal sum | Supported | Supported | `.md5`, `.sha1`, `.sha256`, `.sha512`, algorithm-specific |
| BSD tagged checksum | Deferred | Deferred | algorithm-specific text files |
| JSON result schema | Not applicable | Supported (CLI `--json`) | `.json` |

New formats require fixtures, collision/ambiguity analysis, encoding behavior,
and an ADR when they change the public compatibility contract.

## 3. GNU-Style Records

The canonical generated representation is:

```text
<lowercase hexadecimal digest><space><space><relative path>
```

Binary/text marker variants may be read for compatibility. Generation uses
forward slashes by default for portable relative paths. Ambiguous escaping must
be explicitly documented and tested before support is enabled.

Records may carry any digest listed in [Algorithm Policy](ALGORITHMS.md). When
the caller supplies no algorithm context, the parser deduces it from digest
length only where that length is unambiguous (MD5, SHA-1, and SHA-384). Lengths
shared by several algorithms follow the GNU conventions: eight hexadecimal
characters mean CRC32 and 64 mean SHA-256. Remaining ambiguous lengths (for
example 16 characters for XXH64/XXH3 or 128 for SHA-512/SHA3-512/BLAKE2b-512)
are rejected rather than guessed. CRC and xxHash digests are written big-endian
so the text matches the canonical numeric value.

## 4. SFV Records

Blank lines and lines beginning with a semicolon are comments. A data line ends
with an eight-digit CRC32 value separated from the file name by whitespace.
Parsing proceeds from the digest at the end so spaces in file names remain
representable. Generated CRC values use uppercase hexadecimal. SFV carries
CRC32 only; CRC32C and xxHash values are not representable in SFV and belong in
GNU-style manifests.

## 5. Encoding

Readers use this precedence:

1. Honor a recognized BOM.
2. Accept valid UTF-8 without a BOM.
3. Apply an explicitly selected legacy encoding, if available.
4. Otherwise report an encoding error; do not silently replace bytes.

Writers default to UTF-8 without BOM and LF line endings. Optional UTF-8 BOM,
UTF-16 LE with BOM, and platform line endings are compatibility settings.

## 6. Paths

- Generated manifests use paths relative to the manifest location or an explicit
  root.
- Absolute paths are not generated by default.
- Readers reject NUL characters and invalid path records.
- Lexically resolved entries may not escape the approved root through `..`.
- Symbolic links and junctions follow the active traversal policy.
- Platform-incompatible paths are reported, never rewritten silently.
- Duplicate normalized targets are retained as separate source records but
  clearly diagnosed.

## 7. Algorithm Detection

File extensions and digest length are hints, not unquestioned proof. Ambiguous
digests require a selected algorithm or manifest-level context. The parser must
not guess between algorithms with equal digest length.

## 8. Output Safety

Manifest creation uses a temporary file and atomic replacement when supported.
Existing output is never overwritten without explicit user intent. A manifest
must not include itself unless that behavior is explicitly requested and
documented.

## 9. JSON Schema

Machine-readable output carries a top-level `schema_version`, application
version, job outcome, algorithms, and result records. Paths include a readable
representation and may include a platform-specific lossless representation.
The schema will be finalized before the CLI is declared stable.
